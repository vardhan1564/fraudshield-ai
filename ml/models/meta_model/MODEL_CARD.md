## Purpose
Combines the model scores into one calibrated `risk_score` (0-1) and decides APPROVE / STEP_UP / HOLD. This is the score the API serves.

## Training data
The validation split's base-model scores (out-of-sample for every base model); thresholds chosen on 5-fold out-of-fold predictions, metrics on test. Base models: txn_model v2 (data hash `6d2f3758d379b4e2`).

Inputs: `txn_score`, `anomaly_score`, `social_eng_score`, `graph_score` (probabilities as logits, standardised). Logistic regression weights:

## Thresholds
- HOLD if risk_score > 0.2661 (validation FPR 0.2%, target ≤ 1%).
- STEP_UP if risk_score > 0.0161 (validation FPR of STEP_UP or HOLD 4.7%, target ≤ 5%).
- Rule (spec 01 F2): ctx_unknown_call and payee_is_new adds 0.25 (capped at 1.0).
- Isotonic calibration: risk_score reads as a fraud probability.

## Limitations
- Trained on simulated UPI data: scam signatures are cleaner than real life, so simulated scores overstate real performance (the IEEE-CIS benchmark is the realistic reference).
- `graph_score` is the payer's GraphSAGE score at payment time (snapshots every few hours offline, every 5 minutes online), so offline it is slightly staler than in production.
